# movisda extracts取得と一県インデックスの実証記録

## 現在の結果

2026-11-08にmovisda extractsの東京都(`/admin/JP-13-latest.osm.pbf`)を実取得し、条件付き再取得とpyosmiumによる一県走査のインデックス試作を確認した。タスク2.5を完了した。確認を残したのは公開メタデータと集計値のみで、個人の値は表示・保存していない。以下に実測と判断を保持する。

## 都道府県抽出の取得実測

- `https://osm.download.movisda.io/japan/tokyo-latest.osm.pbf` はHTTP 302で `/admin/JP-13-latest.osm.pbf` に解決され、`Content-Disposition: attachment; filename="JP-13-202611070100.osm.pbf"`、`Content-Type: application/x-pbf`、132,516,215 bytes を応答した(応答時刻 2026-11-07T20:01Z)。
- 応答は `ETag: "258937993"` と `Last-Modified: Sat, 07 Nov 2026 01:00:00 GMT` を伴い、`Accept-Ranges: bytes` を示す。抽出は日次(01:00Z基準)であり、ETagは版ごとに変化する。
- HEAD要求にもETag・Last-Modified・Content-Lengthが含まれるため、取得前にサイズと更新の有無を確認できる。
- 保存済みETagを `If-None-Match` に付けた再要求はHTTP 304(所要1.3秒)で応答し、既存の132MBファイルを維持して再ダウンロードしないことを実ネットワークで確認した。304応答にはETag・Content-Lengthが含まれないため、304時は前回状態(ETag・Last-Modified・サイズ・ファイル名)をそのまま保持する必要がある。

## 実装物とfixture検証

- `src/paperphone/osm_extracts.py`: 都道府県URL(JP-01北海道からJP-47沖縄までのISO 3166-2対等コード)、前回状態から条件付き要求(ETag優先、無ければLast-Modified)を決定する純stdlibの部品。応答ヘッダーの状態はディスクに書かず呼出し側へ返す。304時の状態維持、200時でのヘッダー更新、非PBF応答・再検証用ヘッダー欠落・異常なContent-Lengthの拒否を実装した。
- `tests/test_osm_extracts.py` と `tests/fixtures/movisda_tokyo_headers.json`(実測ヘッダーのfixture): 初回と条件付きの要求決定、304での状態維持、200での更新、不正応答の拒否、実測fixtureの解析を13件のunittestで確認した(全件成功)。ネットワーク・GI不要で `PYTHONPATH=src python3 -m unittest tests.test_osm_extracts` で再実行できる。
- `tools/probe_osm.py`: `--mode meta`(HEAD確認)、`--mode download`(条件付き取得の実行と状態更新)、`--mode scan`(pyosmium走査集計)の3動作。実ネットワーク要求は自動再試行せず、失敗は分類だけを出力する。取得状態(`build/cache/tokyo-state.json`)は公開メタデータのみを保存する。

## 一県インデックス試作の集計(東京都・JP-13-202611070100.osm.pbf)

- PBF 132,516,215 bytes を `osmium.FileProcessor` + `osmium.filter.KeyFilter("name")` の一巡で走査し、所要は **2.6秒**(2026-11-08、pyosmium 4.3.2 / rapidfuzz 3.14.6 / shapely 2.2.0 の `.venv-geocoding`)。
- 試作が保持した名前の異なるノード候補は **114,460**（同名の複数ノードを落としているため全ノード数ではない）。名前つきウェイ **123,855**（うち道路 `highway=*` が **34,468**）、リレーション **13,890**を別集計した。
- 多いウェイの種別: `other` 51,270 / `highway=primary` 6,540 / `railway=rail` 6,531 / `highway=secondary` 5,568 / `leisure=park` 5,543。
- 試作の簡易メモリ概算は **約7.4MB**（名前のUTF-8バイト合計と定数の積算）。Pythonオブジェクトや幾何処理を含む実メモリ測定ではなく、本番インデックスの必要メモリを示さない。完全版の計測は後掲6.2を参照。
- 曖昧照合(rapidfuzz `WRatio`、114,460件の名前に対しlimit=3)は **52ms** で完了し、ローカル検索の応答性能として十分な見込み。

## pyosmium APIの実測メモ

- `FileProcessor(path).with_filter(KeyFilter("name"))` はノード・ウェイ・リレーションを続けて返し、`item.type_str()` は小文字の `"n"` / `"w"` / `"r"` を返す。
- ノードの `item.location` はPBF内に直接含まれるため、追加のロケーションキャッシュは不要。ウェイ・リレーションには位置がなく、道路はタグでの別集計とした(経路グラフはタスク6.3で別途)。
- タグの判定には `TagList.has()` が無く、`dict(item.tags)` に変換してから扱う。
- 同名の要素は最初に現れた1つだけ保持した(プロトタイプの制約。同名地点の区別はタスク6.2の実装課題)。

## 制約と残る検討

- movisdaは境界切りで合成ID(30,000,000,000以上のノードID)と接続切りの途中ノードを用いる。完全なIDを持つ元データとの整合はこの機能に影響しないと見なすが、リレーションが県境で「縮小」される点は経路・描画で留意する。
- 配布依存(pyosmium・rapidfuzz・shapely)の `requirements.txt` 反映は、タスク6.2の統合実装時の判断とする。今回の実証は `.venv-geocoding` 開発環境でのみ実行した。
- 取得頻度は `-latest` とETagで「版が変わるまで1要求」に抑え、再要求制御はMET Norway(第5決定)と同じ思想で統一する。

## 都道府県選択・永続化・更新の実装検証（タスク6.1）

2026-11-08に、内蔵境界のオフライン照合、明示操作によるPBF取得・条件付き更新、版別の保存、GTKでの候補選択と失敗表示を追加した。データと再取得の仕組みはdocs/offline-maps.md、境界資源の出典・再作成方法はsrc/paperphone/resources/maps/README.mdを参照する。

- movisdaの公開indexから日本47都道府県の実境界だけを抽出して同梱した（194,069 bytes）。形状は提供者が一般化したものをそのまま保持し、矩形で代用していない。数値的な境界精度は保証せず、候補は利用者が手動で変更できる。
- 全47県の公開の県庁所在都市、離島、穴・MultiPolygon・共有境界・重複領域、座標の型と範囲、ネットワークを禁止した初回読込を15件のテストで確認した。利用者の現在地を取得した試験ではない。
- 合成PBFと偽HTTPにより、未確認時は要求しない、ETag/Last-Modifiedの条件付き要求、304再利用、抽出基準日の保持、旧版を変更しない更新、403/404/503/通信失敗/不正サイズ/他県応答/権限不足時の旧manifest保持を確認した。SHA-256による破損検出と再取得による修復、10分間隔と429/Retry-Afterの待機も確認した。
- GTK操作テストでは、現在地の候補提示だけでは取得しないこと、位置不明・拒否後の手動選択、明示した更新とオフライン再利用、古い非同期応答が新しい県選択を上書きしないことを確認した。地図取得失敗後も連絡先を選び、地図なしの共通生成スナップショットを作成できた。冊子PDFへの統合は7章・8.1に残る。
- 新しい大容量PBFの実取得はしていない。実通信での東京都取得・304確認は先の2.5の記録を保持する。境界資源の作成時のみ固定の公開indexを取得した。
- 翻訳を生成した上で全204件のテストが成功し、日本語指定の地域関連21件も成功した。実紙の折り畳み・地図描画・経路の完成を示す検証ではない。

## 本番地名インデックスと地点選択（タスク6.2）

- pyosmium・Shapely・RapidFuzzで、ノードに加えて名前付き線・閉じたウェイの面・リレーションの面を読むインデックスを実装した。同名地点はOSM種別/IDで区別し、線上・穴を避けた面内の代表点を使う。日本語・英語・かな・別名タグを正規化して完全一致/部分一致/曖昧一致で検索する。
- GTKビューで出発地と目的地を独立して選び、名称・種別・座標・IDを確認する。現在地を既定候補にでき、結果なし・取消・県外の地点を区別する。取消は遅延結果を破棄し、解析コールバックでも協調的に停止する。libosmiumの内部準備走査は次のコールバックまで中断できない。
- 合成XML/PBFの幾何・穴・同名地点・検索・取消・非通信/非保存を18件、GTKの地点選択を8件で検証した。全体テストをビルドディレクトリからも実行できるようテストパッケージとMesonの探索ルートを整えた。
- 保存済みの東京都PBFを使う完全版の計測は構築100.04秒、検索133.54ms、プロセス最大RSS 700,672KiB（約684MiB）。新規ダウンロードは行っていない。ノード中心の2.5試作より広い幾何を扱うため、2.6秒・7.4MBの概算を完全版へ流用しない。
- Python3.15のプロジェクト内開発環境にosmium4.3.2・Shapely2.2.0を導入し、RapidFuzz3.14.5とGTKの共通環境で試験した。requirementsとMeson構成検査へ依存を追加した。システム全体のパッケージは変更していない。
- Mesonの構成・ビルド・全体テストが成功し、ワークスペース内のステージングインストールでも地名検索モジュール・内蔵境界・日本語翻訳の読込を確認した。製品用Flatpakと画面全体の統合は後続タスクのまま。

## 徒歩経路と紙面モデル（タスク6.3）

- 範囲内の実OSMノードで歩行者グラフを作り、Dijkstra法で経路・球面距離・距離÷1.4m/sの目安時間を得る。車用と徒歩用の一方通行を区別し、通行権・階段・障害物・条件付き制限を保守的に扱う。幾何交差や参照ノード欠落を架空の接続で補わない。
- 明示的な歩行者右左折制限の関係ウェイは全体を除外する。完全な交差点状態ルーターではないため合法経路も失われうる。不完全な歩行者制限はデータ不正として失敗させ、通行可能と推測しない。
- 地点選択と同じ県・同じ版別PBFを検証し、既定2kmの余白付き範囲で計算する。100m以内の実道路ノードへだけスナップし、元の地点からの架空の接続線を経路へ混ぜない。紙面モデルには元の地点・道路上のポリライン・距離・時間・両端のずれ・基準日・出典を保持する。
- 合成XML/PBFによるルーター25件と、選択版・同一点・県外・分断・紙面スナップショット投影6件で検証した。紙面フィールドにはローカルファイルパスを含めない。範囲グラフで経路がないことと、県全体で徒歩移動不能なことを区別する。
- 保存済み東京都PBFの公開都心範囲を読む追加検証は49.79秒、プロセス最大RSS 218,892KiB。公開地点間で603.4m・44点の経路が得られ、両端のスナップ距離は100m以内だった。新規の外部通信・実位置取得は行っていない。任意の経路の現地通行可能性や処理時間は保証しない。

## Cairo印刷地図（タスク6.4）

- 同じPBFから道路等級・水域の穴・建物・公園/森林を読み、Web Mercatorで出発/目的の元座標と全経路点を収めたベクタ地図を描く。架空の接続線は加えず、同一点もA/Bを別表示する。背景ラベルは衝突等で間引く。
- MapLibre互換のOSM Libertyの公開値を参照し、水域/公園/建物の色と下位道路幅を印刷背景・pt単位へ調整した。スタイルJSON・タイル・glyph等を組み込まず、エンジンの画素一致を主張しない。BSD通知とCC BY由来のデザイン帰属・変更説明を同梱し、紙面にも出典を表示する。
- 帰属・ODbL URL・基準日・距離/目安時間・道路までのずれを8pt以上の独立フッターへ置く。収容不能やPBF解析失敗は明示結果とし、出典を削って成功扱いしない。
- 合成XML/PBFの11件と日本語指定の同11件が成功した。水域の穴、道路等級、投影、実経路のみの重ね描き、ベクタPDFの抽出可能文字、同一点、注記のoverflow、不正PBFを確認した。
- 保存済みの東京都PBFと公開の試験地点を使い、A4確認図を作成して目視した。経路用グラフ再読込から地図PDFまで97.35秒、PDF297,982bytes。背景ラベル271件を省略した。新たな通信・現在地取得は行っていない。これは地図単体の確認であり、完成冊子や実紙出力の検証ではない。

## 既知の環境依存失敗(本実証と無関係)

`python3 -m unittest discover -s tests` のローカル直接実行では、`PAPERPHONE_LOCALEDIR`(mesonビルドで設定される)が未定義のため test_smoke の2件が既存から失敗する(2026-11-08確認)。本実証で追加した13件(test_osm_extracts)は無関係に全件成功する。失敗の解消は既存のビルド手順側の課題とする。
