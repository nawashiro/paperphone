# MET Norway直接取得の実証とlibgweather先行検証記録

## 現在の結果

Locationforecast compact JSONの直接取得をGNOME Platform 51で実証し、タスク2.4を完了した。HTTP 200、65件の短期予報、明示的な1時間の期間、Expires有効中のメモリキャッシュ再利用を確認した。座標・連絡先・予報地点・具体的な予報値は表示・記録していない。詳細は末尾の直接取得記録を参照する。以下にはlibgweatherの先行実証と、その時点の制約・判断を履歴として保持する。

## libgweather先行実証の結果

利用者の再許可後、セッショントークンを追加した位置情報ポータル要求と、libgweatherのMET Norwayプロバイダーによる実地点の予報取得に成功した。座標・連絡先・予報地点・具体的な予報値は表示・記録していない。当時はキャッシュの実挙動と天気記号の対象期間の扱いに残作業があり、タスク2.4を未完了とした。

再試行では `CreateSession` 段階で `LocationUnavailable` となった。診断出力には失敗した段階だけを残し、D-Busエラー名・メッセージは保存していないため、具体的な原因は特定できない。後の読み取り専用確認では、セッションバスのLocationインターフェースとGeoClueサービスが稼働していたが、これだけでは再試行時の失敗原因を特定できない。

## 利用者の再許可後の試行

利用者から位置情報の再要求・MET Norwayへの座標送信の許可とクライアント識別用連絡先の指定を受け、一度だけ位置情報を要求した。`LocationPortal.request_once()` は `LocationUnavailable` となり、座標を受信できなかった。自動再試行は行わず、MET Norwayへのリクエストも送信していない。今回の出力は例外の型と未送信の事実のみで、失敗段階・原因は特定していない。連絡先の値・座標・予報値は記録していない。タスク2.4は未完了のままとする。

## セッショントークン修正後の実証

- ポータルとGeoClueは稼働しており、Location API version 1を公開していた。位置取得を開始しない比較では、`CreateSession` の `session_handle_token` 省略時に `org.freedesktop.DBus.Error.NoReply`、一意のトークン指定時にはセッション作成・終了に成功した。省略が失敗に関係している可能性は高いが、ポータル内部の根本原因は未確認。
- `src/paperphone/location.py` にセッショントークンを追加した。`tests/test_location.py` の5件が成功し、有効かつ一意なトークン、拒否後の再要求禁止、サービス失敗時の終了動作を確認した。
- 利用者の再許可に基づきCITY精度で一度だけ位置情報を要求し、座標を取得した。小数点以下4桁以内に切り捨てた座標をメモリ内で `GWeather.Location.new_detached()` に渡した。
- `GWeather.Info` にアプリID、利用者指定の連絡先、`GWeather.Provider.MET_NO` を設定し、一度だけ更新した。88件の予報が返り、全件で予報時刻・摂氏気温・天気アイコンを読めた。アイコン取得成功は全状態の意味や紙面アイコン対応を保証しない。
- 連続する予報時刻の差は、3600秒が59組、21600秒が28組だった。短期と中期が同じ一覧に混在することを確認した。
- 実際にロードした共有ライブラリは `libgweather-4.so.0.600.0`、ホストパッケージは `libgweather-4.6.0-6.fc45.x86_64`。この版での取得成立を確認したが、配布環境での同等性は未確認。
- 4.6.0の `weather-metno.c` はLocationforecast 2.0のclassic XMLを読む。瞬間値の要素へ直後の期間要素の天気記号を合成する一方、その期間の終了時刻を予報項目へ保持していない。今回のGI経由の実通信では元XMLの期間を観測していないため、記号の期間を一律1時間と断定できない。
- 識別情報はAPIへ設定したが、送信ヘッダー自体は観測していない。HTTPキャッシュの有効期限・条件付き再取得も未観測。追加の予報要求は行っていない。

## モック／静的確認で分かったこと（実通信成功前）

- PyGObjectから `GWeather-4.0` 名前空間と `GWeather.Provider.MET_NO` を参照できる。
- `GWeather.Info` の `updated` シグナル、`get_forecast_list()`、予報項目の時刻・摂氏気温・天気状態を読むAPIを確認した。外部予報リクエストは行っていないため、実データが返ることや実地点の時間粒度は未確認。
- 公開されているlibgweatherのMET Norway実装では、予報時刻と気温・状態を `GWeather.Info` 項目として組み立てる一方、天気記号の期間境界を独立した値として保持していない。紙面/UIで期間を示す方法は後続実装で扱う。
- 公式Locationforecast資料では短期と中期で提供間隔が異なり、地域・予報期間による欠損もある。実地点の一覧を得ていないため、この環境の実際の間隔は未確認。
- 規約に従い、今後の実リクエストでは座標を小数点以下4桁以内に切り捨て、Paper Phoneのアプリ名・バージョンと利用者指定の連絡先を識別情報に含め、キャッシュ有効期間内の再取得を避け、出典・ライセンスを示す。今回の実行は位置取得に失敗したため、これらの情報はMET Norwayへ送られていない。利用者指定の連絡先の値はこの記録に含めない。
- 実行環境で確認できたのはGI名前空間 `GWeather-4.0` まで。libgweatherのディストリビューションパッケージ版は、この環境のpkg-config／パッケージ情報から確認できなかった。

## 期間情報・識別・キャッシュの追加調査

実地点への追加要求は行わず、4.6.0のソースと公式データモデルを調査した。

- 公式データモデルは `instant` の気温と、`next_1_hours`・`next_6_hours`・`next_12_hours` の期間変数を区別する。`symbol_code` は期間変数であり、予報時刻の隣接間隔だけから対象期間を確定してはならない。JSONを使うなら、明示的な `next_1_hours` がない項目を短期記号の代替にしない。
- classic XMLでは期間要素の `from` と `to` が根拠になる。libgweather 4.6.0は瞬間値へ次の要素を合成した後、期間境界を公開しない。公開GI APIでも期間・内部HTTPセッションを取得するメソッドは確認できず、`store_cache()` だけでこの欠落を補うことはできない。
- `gweather-info.c` の `ref_session()` は `libgweather/<version> <application-id> (<contact-info>)` をUser-Agentへ設定する。単なるアプリ名・版の設定ではなく、指定したアプリIDと連絡先がこの書式へ入ることをソースで確認した。実際の送信ヘッダーの観測ではない。
- `get_cache()` は `$XDG_CACHE_HOME/libgweather` に `SoupCache` を作り、読み込み・終了時のダンプを行う。したがって、アプリ独自のファイル保存を行わなくても、HTTP応答や座標入りURLがライブラリのディスクキャッシュに残る可能性がある。先行実証での実際の書込み有無は確認しておらず、「永続化なし」が保証されたとは扱わない。既存の共有キャッシュは他アプリのものと区別できないため、削除しない。
- libsoupへキャッシュを委譲する実装は確認できるが、Expires・条件付き再取得の実挙動は未検証。位置情報を永続化しない制約も含め、アプリ専用のキャッシュ方針が必要になる。

### 補完方法の比較

1. **libgweatherを維持し、期間取得APIとキャッシュ制御を追加した版を同梱する**：同じHTTP応答から時刻・記号・期間を得られ、取得元の整合性を保てる。ライブラリの変更・保守と配布構成の追加が必要で、現在の計画外。
2. **MET Norway Locationforecast JSONをアプリのアダプターから直接取得する**：`next_1_hours` の明示的な期間とHTTPキャッシュヘッダーを扱いやすく、メモリのみのキャッシュも実装できる。ただしlibgweather経由という現在の設計・タスクを変更する必要がある。
3. **libgweatherとは別に元データを取得して結合する**：二重取得となり、更新時刻の違う応答を誤結合する危険がある。単純な時刻一致だけでの結合は採用しない。
4. **一覧の時刻間隔から期間を推定する**：保証できない期間を捏造するため採用しない。

直接JSONを扱う方式が期間・メモリキャッシュの要件を最も単純に満たせるが、現在の設計を無断で置換しない。libgweatherの維持を優先する場合は、対応版の同梱という追加スコープが必要になる。

## libgweather先行実証時の判断と残作業

実地点の取得には成功したが、期間情報の欠落とキャッシュの永続化という設計上の問題が残る。取得方式・配布依存・位置情報の保持方針を整合させる計画変更が必要である。送信ヘッダー・キャッシュ挙動の検証と配布環境との照合も残っており、タスク2.4は未完了のままとする。追加の位置情報・予報要求は行っていない。

## 直接JSON取得への切替後の実装と試行

- 利用者から規約への同意、現在地の再取得・MET Norwayへの送信許可、識別用連絡先の指定を受けた。連絡先の値はこの記録・コード・診断出力へ保存していない。
- `src/paperphone/weather.py` にLocationforecast 2.0 compact JSONの直接取得を追加した。Python標準ライブラリのHTTPS/JSON処理を使い、libgweather・libsoup・ディスクHTTPキャッシュは使用しない。メモリには直近の地点・正規化予報・HTTP検証用ヘッダー・取得／検証時刻だけを保持する。要求・応答・識別情報をログへ出さず、urllib由来の詳細例外も外へ渡さない。
- `instant.details.air_temperature` の摂氏瞬間値と `next_1_hours.summary.symbol_code` を読み、UTCの対象時刻と1時間後の期間終了を保持する。1時間の期間情報がない中期予報や不正な値は除く。未知記号は別の天気へ置き換えず、そのまま保持する。
- 小数点以下4桁への切捨て、アプリID／版／連絡先を含むUser-Agent、gzip／deflate、Expires、Last-Modified／ETagによる条件付き取得と304、429の秒数／HTTP日付Retry-Afterを実装した。期限欠落・不正応答・通信失敗時の最短再取得間隔は10分とする。失敗時に古い予報を新規取得成功として返さない。
- Meson 1.6.1でビルドと全125件のテストが成功し、`openspec validate migrate-to-gnome` も成功した。翻訳ディレクトリ未指定の直接unittest実行では既存の翻訳テスト2件が失敗したが、翻訳をビルドして参照するMesonの正規構成では全件成功した。`tests/test_weather.py` の13件が成功した。実座標・実連絡先を含まないfixtureによる検証であり、実サービスが304を返したとの主張ではない。UIとPDFへの統合・出典注記は未実装で、タスク5.1〜5.4は未完了。
- `tools/probe_weather.py` は許可済みの利用者向けに、連絡先を非表示入力または標準入力から読み、一回だけ位置取得・予報取得を行う再実行用の実証ツールである。成否・件数・ヘッダーの有無のみ出力し、値の記録や自動再試行を行わない。実行には利用者の許可を必要とする。今回の調査では再要求も含む継続調査の許可を得ているが、通常アプリの拒否後の自動再要求は引き続き禁止する。
- 配布候補のGNOME Platform 51でPython 3.14.9、OpenSSL 3.5.9、GLib 2.90.1を確認した。HTTP／JSON処理に追加のPythonパッケージは不要。
- 同ランタイムの最小権限サンドボックスでホーム・ホスト全体へのアクセスを禁止し、`src/` と `tools/` のみ読取許可して一度試行した。Locationポータルが拒否／取消の応答を返し、`LocationDenied` で終了した。意図的な拒否かどうかは断定しない。座標は取得できず、MET Norwayへの予報要求は送っていない。自動再試行は行っていない。

### フォーカス制約の切り分けと直接取得の成功

- 過去の`session_handle_token`修正は適用済みのまま保持した。今回の再調査では、そのトークンを渡してもLocationポータルが応答`2`を返すことを確認した。XDG Request仕様の`1`は利用者の取消、`2`はその他の終了であり、両方を`LocationDenied`としていた誤分類を修正した。数値応答だけを診断へ渡し、応答本文は記録しない。
- ポータルのログに「フォーカス中のアプリだけがシステムアクセスダイアログを表示できる」というAccessDeniedと、親ウィンドウとの関連付け失敗があった。GNOMEの位置情報設定、GeoClue、Locationポータルはいずれも有効だった。前回の`LocationDenied`記録は意図的な利用者の拒否を示すものではない。
- `Start`前にトークンから予測したRequestパスのResponseを購読するよう修正した。旧ポータルが別パスを返した場合は購読先を差し替える。これは高速応答の取りこぼし防止で、今回のフォーカス制約とは別の改善である。`CreateSession`のセッショントークンも引き続き一意にする。
- `tools/probe_weather.py --window`でGTKウィンドウを提示し、フォーカス後にWaylandのexport済みハンドルを`parent_window`として渡した。借用サンドボックスのアプリIDとウィンドウのアプリIDを一致させた。バス全開放、ホームアクセス、恒久権限変更、ポータル／GeoClueの再起動は行っていない。
- この方式で位置取得とMET Norway直接取得に成功した。User-Agentへ指定の識別情報を渡したこと、HTTP 200、gzip、ExpiresとLast-Modifiedの存在を確認した。ETagは実応答になかった。HTTPS上のヘッダーのパケット復号やサーバー側ログ確認は行わず、アダプターへ渡す送信ヘッダーと標準ライブラリの要求生成を確認した。
- 実JSONから65件の短期予報を正規化でき、全件のUTC時刻・摂氏気温・状態記号・明示的な1時間の期間を保持できた。直後の同地点の取得呼出しは同一のメモリキャッシュを返し、予報サービスへの実通信は1回だけだった。応答は非推奨製品を示す203ではなく200だった。
- 有効期限前の追加要求は行っていない。期限切れ条件付き取得と304、429／Retry-After、期限欠落、通信失敗は応答fixtureで確認したもので、実サービスからこれらの応答を受けたという主張ではない。
- アダプターにディスクキャッシュ／ログ書出しを設けず、応答は取得処理内と正規化結果のメモリ内だけに保持する。識別情報は標準入力から読み、実証の出力は上記の成否・件数・ヘッダー有無のみ。libgweatherの既存共有キャッシュは読取・削除とも行っていない。
- 修正後のMesonビルド・全127件のテスト、OpenSpec検証が成功した。
- **タスク2.4完了**。UIでの非同期取得・精度不足表示・時刻選択・紙面出典の統合は後続タスクに残る。

## UI・紙面モデル・出典描画の検証（2026-11-08）

- 5.1では当初誤差半径10kmの制限を実装して試験したが、同じ日（2026-11-08）の追加の利用者判断により撤去した。撤去後はシステムが返す精度値を上限なしで扱う。5.2の時刻選択を用いて実予報時刻・1時間の対象期間・取得時刻・再確認時刻を不変の紙面モデルへ投影した。GTK表示と共通生成スナップショットに同じデータを渡し、9時枠の9時30分予報を9時と偽らない。未知コードは元のコードと未知表示を残す。
- 既知コードの判定はMET Norway公式weathericonsのlegend.csv（下記）を参照した。画像資源は取り込んでいない。
- Cairo/Pangoによる天気ブロック描画を追加し、本文と出典の領域を分離した。出典にはMET Norway、抜粋・整形、CC BY 4.0、ライセンス参照URLを含める。本文が収まらない場合は呼出し元へ超過を通知し、帰属自体が収まらない領域ではエラーにする。
- 合成予報からメモリ内でPDFを生成し、Popplerのテキスト抽出で実時刻・期間・未知コード・出典・ライセンスURLを確認した。小領域での本文超過時も出典を保持することを確認した。実紙の可読性と8区画冊子への配置は7章・8.4で確認する。
- Expires・Last-Modified/ETag・304・429/Retry-After・期限欠落・通信失敗の既存fixture試験に加え、初回304の拒否、期限不明・期限切れの紙面状態、HTTP層の非保存・非ログ出力を偽transport/streamで検証した。新たな実座標の取得・予報サービスへの実通信はしていない。
- 翻訳カタログをmsgfmtで生成した上で全171件のunittestが成功した。日本語指定の天気UI・紙面・PDF関連11件も成功した。OpenSpecのタスク5.3・5.4に対応する部品の検証であり、全画面統合・冊子レイアウト・配布環境の完了を意味しない。
