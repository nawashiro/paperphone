# 位置情報ポータル実証記録

## 実証結果

- セッションバスのXDG Locationポータル（API version 1）を利用。GeoClueのセッションバス名はこの環境では稼働していなかったが、ポータル経由の要求は成功した。
- 利用者の許可後、天気用途に必要な市区町村相当（CITY）の精度で一度だけ要求し、有効な緯度・経度ペアを受信した。座標値は表示・ログ出力・ファイル保存せず、受信直後に破棄してポータルセッションを閉じた。
- 2.3の初回実証では自動再要求を行っていない。その後の2.4検証では、利用者の個別許可に基づく追加要求が座標受信前に失敗した。最終試行では`CreateSession`段階の失敗を確認したが、D-Busエラー名は保存していない。いずれも座標取得・MET Norway送信には至らず、追加の再要求は行っていない。許可拒否の実ダイアログ試験は追加プロンプトを出さないため未実施。代わりに`tests/test_location.py`で拒否応答後に開始要求が再発行されないこと、ポータル停止・応答失敗時に再試行せずセッションを閉じることをモック試験した。

## 直接JSON取得時の追加調査

過去に確認した`session_handle_token`省略による失敗とは別に、今回のヘッドレスFlatpak要求ではGNOMEのフォーカス制約が問題になった。一意のセッショントークンを渡した状態でも応答`2`（利用者の取消`1`とは異なる）を受け、ポータルログにフォーカス中のアプリだけがアクセスダイアログを表示できる旨と親ウィンドウ関連付け失敗を確認した。システムの位置情報設定とGeoClueは有効だった。

再要求も含む継続調査の許可に基づき、GTKウィンドウをフォーカスさせ、そのexport済みWaylandハンドルをLocationPortalの`parent_window`に渡したところ、同じGNOME Platform 51サンドボックスで座標取得とMET Norway直接取得に成功した。恒久権限変更やサービス再起動は不要だった。座標・連絡先・予報値は記録していない。詳細は `metno-validation.md` を参照する。

実装は応答1と2を区別し、Start前にResponseを購読するよう修正した。通常アプリの拒否後の自動再要求禁止は変更しない。

## データ送信の説明

Paper Phoneが天気を取得する場合、許可された位置から得た座標をMET Norwayの予報サービスへ送信する。座標は天気取得のリクエストにのみ使い、ログや永続キャッシュへ残さない。XDG Locationポータルの実装が位置をどのローカル／外部プロバイダーから得るかはOS構成に依存するため、アプリはシステムの位置情報許可画面に委ね、拒否・利用不能時に独自の外部位置推定へ切り替えない。

天気機能を使わない場合は位置情報を要求しない。位置情報が拒否または取得不能なら天気を利用不能と表示し、再要求せず、他の冊子機能を続けられるようにする。
