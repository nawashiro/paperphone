# Design

## Context

調査の出発点はCoMaps（`comaps/comaps`、commit `ae946a18`）の生成パイプラインである。要点は、実行時の負荷を全部ビルド時に押し込み、実行時は既に配置された答えだけを読むという思想で、具体的には次の三機構が当てはまる。

- **metalines**（`metalines_builder.cpp`）: 同じ属性のway同士を交差点の接続まで見て事前に統合し、1本の見た目の通りを1レコードにする。
- **簡素化の前倒し**（`generator_tool` 第3パス、`scales.hpp`・`feature_impl.hpp`）: スケール行ごとのε（Douglas–Peucker）を構築時に決めて格納し、実行時は該当行の幾何だけをパースする。
- **ランクの1バイト化**（`FEATURE_STRUCTURE.md`、地点地物に人口を log 評価した1バイト）: 描画の取捨選択をランクで行う。

paperphoneの派生データ（`osm_derived.py`）は、道路をway単位の全頂点（投影座標の折れ線BLOB）、ラベルを（name, x, y）のみで持つ。簡素化と統合の処理は構築側に存在しない。印刷地図（`map_rendering.py`）は照会結果を等価に描き、ラベルの省略は描いた順の重なり判定で決まる。

紙面地図は縮尺が一枚ごとに決まり、標高やタイルといった他の用途を持たない。このためCoMapsの4スケール行（世界系{3,5,7,9}・国系{10,12,14,17}）の完全な再現は過剰であり、εの1段階で足りる。

## Goals / Non-Goals

**Goals:**

- 構築時の1回だけで、派生データの格納点数を実質的に減らす（道路の統合、幾何の簡素化）。
- 紙面で判別できる精度を保つ。簡素化による見た目の劣化を印刷PDFで確かめる。
- ラベルの省略が重要度を守る。既存の重なり回避の仕組みは流用する。

**Non-Goals:**

- 複数段階の簡素化幾何（スケール行ごとの格納）は作らない。実行時に縮尺が変わる用途は無い。
- 座標のビット操作・varint再符号化はしない。SQLiteのBlobのままにする。
- 検索・経路・地物照会の応答形式（area特集・road特集・label特集）を変えない。
- ラベルの省略数の報告など描画枠の振る舞い（`MapRenderResult`）は変えない。

## Decisions

**D1: 簡素化は構築時に、εは1段階で一定値。**
道路折れ線と面のリングにDouglas–Peuckerを適用し、許容値はWeb Mercatorメートルの定数（既定1.0m）とする。根拠は、歩行冊子の典型的な表示範囲（数百メートル〜2km）で1mのずれが線幅1.9pt前後に収まり判別できないこと。最小表示範囲100m（`draw_walking_map`の保証）では1mが数ptに伸びるため、視認できる劣化が出ないかPDFで確認する作業をtasksに置く。代替案:

- 実行時の簡素化 — 毎回同じ計算を繰り返し、照会の速さと描画の速さを両方落とす。不採用。
- CoMaps式の複数スケール行格納 — 格納が増え、実行時に縮尺が決まらない用途でもない。KISSの原則により不採用。

簡素化で幾何が無効になった対象は、簡素化していない元の幾何を格納する。紙面の形状を保つ方が、点数の目的のための欠落より優る。

**D2: 道路の統合は、同じ種別で端点が一致する連鎖のみ。**
種別（`road_class`）が同じwayのうち、あるwayの終点が別のwayの始点と一致する場合に連鎖を組み立てる。分岐・交差点（3本以上の一致）は統合しない。根拠はCoMapsのmetalinesが同様に連鎖を単位とする点と、統合しすぎると描画順とcasingの破れが出ること。リング状に閉じる連鎖も1レコードとする。

**D3: ラベル重要度は発生源の種別から決める1バイト。**
`place=city/town/village/suburb/hamlet`、駅、公共施設など発生源タグから固定のランク表で0〜255を与える。populationタグはデータ欠落が多く解釈も重いので読まない。照会は重要度が高い順に並べて返し、`map_rendering.py` の既存の重なり判定はその順に通過したラベルを「先に置いたものが残る」形でそのまま使う。ラベルの矩形判定・省略数の報告は変わらない。

**D4: 派生データの版を2に上げ、旧版は既存の破棄経路へ従う。**
スキーマ差（列追加・格納内容の変化）は外部契約の変化であり、`DERIVED_VERSION` の更新で再構築と旧版削除が自然に起きる。読み替えはしない。

## Risks / Trade-offs

- [簡素化が橋・さくのような細部で形を変える] → εを定数に保ち、PDFの目視確認をtasksに置く。劣化が見えればεの値だけを下げる（構造は変わらない）。
- [統合で描画順がway単位から連鎖単位に変わる] → 種別ごとの幅階層（`ROAD_STYLES`）で描く仕組みは不変で、連鎖内部の順序は見た目に影響しない。テストで種別ごとの描画順を確認する。
- [重要度のランク表が一般の呼び方とずれる] → 表はコードの1か所に置き、値の調整を局所化する。描画は省略対象の選び方が変わるだけである。
- [ビルド時間が増える] → 簡素化と統合は同じ走査パス内の後処理で、N+1走査をしない。実抽出で生成時間の前後をtasksで記録する。

## Migration Plan

版を上げるだけである。次回の抽出版の構築で新版ができ、旧版は既存の掃除で消える。実装の取り消しは版を1に戻すことでは整合しないため、元に戻るときはコード側の変更をrevertする。

## Open Questions

なし。εの値（1.0m）と、それを裏付けるPDFの目視は実装側の確認事項とする。
