# Design

## Context

現在の応答経路は三本とも一県PBFを直接読む。

- 地名検索: `place_selection.py` が初回にPBF全文をメモリ索引化し、版別（都道府県＋sha256）のJSONキャッシュを一時ディレクトリに書く（`PlaceIndex.cache_path`）。
- 徒歩経路: `WalkingRouter.from_pbf` がbounds付きでPBFを走査する。目的地が替わるたび新たなboundsとなり、再び全文スキャンが動く。walking_sheet.py はキー `(path, bounds, max_snap_m)` 単位でルータを保持する。
- 地図地物: `map_rendering.py` が座標bounds付きでPBFを走査し、（パス, bounds）単位のJSONを一時ディレクトリへ書く。

抽出の入手・版別管理は `osm_store.py` が担い、`CachedExtract`（sha256・basis）が既にある。実行モデルは1本の ThreadPoolExecutor と GLib への投稿である。

## Goals / Non-Goals

**Goals:**
- 検索・経路・地物のすべての応答を、抽出版が変わらない限りSQLiteの派生データへの照会に置く。
- PBF全文走査は「抽出版ごとに1回」へ圧縮する。初回生成は進捗表示と取消しを提供する。
- 派生データには利用者由来の情報を含めない（検索語・選択履歴なし）。

**Non-Goals:**
- 経路アルゴリズムの性質変更、地図の描画品質・配色、抽出元URLと更新戦略の変更。UI再構築は別変更（simplify-ui-flow）で扱う。

## Decisions

**派生データの形式: 標準ライブラリの `sqlite3`**
SQLite 1ファイルにテーブルを置く: `places`（名称・別名・種別・緯度経度・OSM id）、`geo_nodes`（id・緯度経度）、`ped_ways` と `ped_way_nodes`（歩行対象のwayとnode接続）。node・wayのidと座標の境界用索引で照会する。FTS5など全文検索エンジンは、現行の正規化（NFKC＋カタカナ→ひらがな）と「あいまいで絞りすぎない部分一致」を保ちたいがため複雑になるので使わない。MeCab等の追加依存も増やさない。

**生成のタイミング: 取得・更新直後に一度だけ**
`osm_store` が抽出を保存した後、その版（sha256）に対する派生データを既存ワーカースレッドで生成する。進捗と取消しは既存の読込UIに接続する。生成の途中状態を出さないため、完成後にアトミックに置換する。版が替わった時だけ再生成する。

**歩行者グラフは生成時に抽出済みにする**
node・wayは生成時に歩行対象だけへ絞って保存する（現行 `_scan_pedestrian` の `_access`・`_way_directions`・`_node_passable` 判定を再利用）。経路時は出発・到着の座標から接近ノードを範囲照会して取り、必要なグラフ部分だけを読む。探索窓の考え方は現行 `max_snap_m=100m` を踏襲し、県全域をメモリで読まずに済ませる。

**旧物の撤去**
`PlaceIndex.from_pbf` とそのJSONキャッシュ、経路・地物のための実行時PBF走査、`map_rendering` の地物JSONキャッシュを破壊的に削除する。旧経路を保つ二重実装・フォールバックは作らない（KISS）。旧版の派生データが残っていても版不一致で棄てる。

## Risks / Trade-offs

- [大都市の派生データが大きくなる] 東京などで数百MBになり得る。→ 座標は実用精度の丸めにし、wayは歩行対象に絞る。実測値を検証時に記録し、必要なら歩行対象の絞りを根本から見直す（設計の再検討）。
- [接近ノードが範囲内に無い地点で経路を得られない] → 現行仕様どおり「経路なし」を明示し、架空の経路は描かない。
- [初回生成の待ち時間は残る] → 生成中は検索・経路を待たせ、進捗を示す。抽出の自動更新による再生成は通知なく裏で行い、利用者に別の作業を強制しない。

## Migration Plan

旧JSON・メモリ索引の互換移行はしない。版の初回起動時に派生生成が走り、生成が済むまで地図機能を使わない冊子作成が続く（現行specの「取得失敗時に冊子を続ける」の振る舞いを維持）。

## Open Questions

なし。派生データの実測サイズは検証タスクで確認するに留める。
